3. Important Problems / Missing Pieces

❌ Critical 1 — Admin API authorization The admin endpoints need explicit authentication + admin-role checks. Never rely on the admin UI alone for security.
❌ Critical 2 — Booking API authorization User-facing booking endpoints must use the authenticated user from the server session/token, not values sent by the browser.
❌ Critical 3 — bookings need a real user relationship Add bookings.user_id so the database knows which authenticated user owns the booking.
❌ Critical 4 — Room assignment must be persistent A booking should permanently identify the assigned room instead of relying only on a recalculated display allocation.
❌ Critical 5 — Payment verification is missing from the booking lifecycle Calculating an advance amount in the database is not the same thing as proving payment was received.
⚠️ Important — Reviews need booking verification Add reviews.booking_id and require a completed booking before allowing a review.

Double-booking prevention

Use the overlap rule:

existing.checkIn < newCheckOut
AND
existing.checkOut > newCheckIn

If a conflicting active booking exists, reject the new booking.

Date rules

✅ check-in before check-out
❌ check-out equal to check-in
❌ check-in after check-out
❌ invalid/past dates according to your booking rules

Price calculation

Never trust the amount sent by the browser. The backend should calculate nights, price, fees/tax if applicable, and the final total from server-side data. 
nights × server-side room/listing price = base amount
base + fees + tax = total amount

Example

Room 1 10–13 Oct → Booked
Room 2 10–13 Oct → Available
Room 3 10–13 Oct → Maintenance
Room 4 10–13 Oct → Available

For a user booking 10–13 Oct, the backend should select a real available room and persist that assignment.

Why persistent assignment matters

If allocation is recalculated every time the admin page loads, a booking can appear to move between rooms. A production booking should have a stable room assignment once assigned.
